# RCA — pergola-tracker: all Mongo-touching endpoints 500 in production

Run: c534d7f0-5c68-48da-a75f-91e5a44ada92 (active, status=success) · template farm_ts_react_mongo · tier_0
Follow-up to RCA_c534d7f0 (domain/SSL). Domain & routing are fine. This is a **runtime code bug**, not infra, not DB connectivity, not secrets.

## TL;DR
The MongoDB **client is NOT unreachable** and the data **is present**. Every DB op 500s because the `motor` client is bound to a **different asyncio event loop** than the one uvicorn uses to serve requests in production. The fix is a few-line change in the app source (create the motor client lazily / inside the serving loop). I reproduced the exact error and verified the fix in the sandbox.

It is **NOT** `ServerSelectionTimeoutError`, **NOT** an auth failure, **NOT** a DB-name mismatch, and **NOT** a TLS/SSL requirement. `/api/` (no DB) returns 200 because it never touches the client; every endpoint that awaits a motor op raises the loop-mismatch `RuntimeError` → FastAPI returns 500.

Nothing to re-seed.

## Root cause (code)
`backend/lib/db.py` creates the motor client at **module import time**:
```python
mongo_url = os.environ["MONGO_URL"]
client = AsyncIOMotorClient(mongo_url)        # <-- bound at import, outside the serving loop
db = client[os.environ["DB_NAME"]]
```
In production, uvicorn is launched **without `--reload`** (the farm `entrypoint.sh` strips `--reload`: `COMMAND=$(echo "$COMMAND" | sed 's/--reload//g')`). The loop uvicorn ends up serving requests on is **not** the loop the motor client latched onto, so every awaited op produces a Future on the wrong loop → `got Future attached to a different loop`.

**Why preview works and prod doesn't:** preview runs the identical code **with `--reload`** (see `etc/supervisor/conf.d/supervisord.conf`: `uvicorn server:app ... --workers 1 --reload`). The reload launcher imports the app inside the serving-loop context, so the client and the request handlers share one loop and there is no mismatch. Strip `--reload` (prod) and the import-time loop ≠ serving loop.

### Other module-level bindings with the same defect (must be fixed too)
These build a GridFS bucket from `db` at **import time**, so they inherit the same wrong-loop binding (used by branding-logo, documents/evraklar, proforma file endpoints):
- `routers/branding.py:21` → `bucket = AsyncIOMotorGridFSBucket(db, bucket_name="branding")`
- `routers/documents.py:38` → `bucket = AsyncIOMotorGridFSBucket(db, bucket_name="evraklar")`
- `routers/proforma.py:50` → `bucket = AsyncIOMotorGridFSBucket(db, bucket_name="evraklar")`
- (`routers/portal.py:222` already builds the bucket inside a function — fine, leave it.)

## Reproduction + fix verification (eph sandbox, no prod secrets)
I reproduced the EXACT production error and confirmed the fix flips it:

**Repro (import-bound client, served on a different loop) → production error:**
```
IMPORT-BOUND CLIENT, served on new loop -> RuntimeError : Task <Task pending ...>
  got Future ... attached to a different loop
```
**Fixed (client created lazily on first use, inside the serving loop) → loop error gone:**
```
LAZY CLIENT, served on new loop -> ServerSelectionTimeoutError : 127.0.0.1:27777 Connection refused ...
```
The `ServerSelectionTimeoutError` is expected in the sandbox (no Mongo/secrets there). The point: the `RuntimeError: ... attached to a different loop` **disappears** once the client is created inside the running loop. Against the real, reachable production Mongo this path returns data normally.
Caveat (honesty): I reproduced the loop mechanism in isolation; I could not run the full uvicorn+uvloop server (uvloop absent in sandbox, no prod secrets). The fix below is loop-selection–agnostic and correct regardless of which loop uvicorn picks.

## Recommended fix (E1 applies in source, then redeploy)
Goal: ensure the motor client is created **inside the serving event loop**, while keeping the existing `from lib.db import db` call sites working.

**`backend/lib/db.py`** — stop creating the client at import; create it lazily via a proxy:
```python
_mongo_url = os.environ["MONGO_URL"]
_db_name = os.environ["DB_NAME"]
_client = None

def get_client() -> AsyncIOMotorClient:
    global _client
    if _client is None:
        _client = AsyncIOMotorClient(_mongo_url)   # binds to whatever loop is running at first use
    return _client

def get_db():
    return get_client()[_db_name]

class _DBProxy:            # keeps `from lib.db import db` + `db.<collection>` working unchanged
    def __getattr__(self, name): return getattr(get_db(), name)
    def __getitem__(self, name): return get_db()[name]

db = _DBProxy()

class _ClientProxy:        # keeps server.py's `client.close()` working
    def __getattr__(self, name): return getattr(get_client(), name)

client = _ClientProxy()
```
First real use is the lifespan startup tasks, which run on uvicorn's serving loop → the client binds there → all request handlers (same loop) succeed.

**`routers/branding.py`, `routers/documents.py`, `routers/proforma.py`** — build the GridFS bucket **inside the handlers** (or via a small helper) instead of at module import, e.g.:
```python
from lib.db import get_db
def _bucket():
    return AsyncIOMotorGridFSBucket(get_db(), bucket_name="branding")  # "evraklar" in documents/proforma
```
and call `_bucket()` where `bucket` was used. This keeps GridFS bound to the serving loop too.

(Alternative if you prefer no proxy: create the client in the `lifespan` startup and expose it via `app.state`/a getter — functionally equivalent. The proxy is the smaller diff given how widely `db` is imported.)

## Secondary (non-blocking) — CORS
Production secret `CORS_ORIGINS = "*"`, which is incompatible with `allow_credentials=True` (credentialed cookie auth). You have already changed `backend/server.py` to drop `"*"` and allow origins via regex for `*.emergentagent.com`, `*.emergent.host`, `*.diagonalventure.com` — that ships with the next deploy and resolves it in code. No secret action is required if server.py no longer reads `CORS_ORIGINS` from env. If any path still reads that env var, note `CORS_ORIGINS` is an **existing** deployment secret and its value can only be changed from the UI (Deployment Panel → Secrets); redeploy does not overwrite an existing secret value. This is NOT the cause of the 500s.

## Bottom line
Mongo is healthy, bound, and fully seeded. The blocker is a code-level event-loop binding bug (`lib/db.py` + 3 module-level GridFS buckets). Apply the lazy-client fix, deploy, and the DB endpoints will return 200.
